## TL;DR — Mặt nạ "CMS → Worker"

Có **3 channel duy nhất** từ CMS sang worker. KHÔNG có direct HTTP RPC (worker URL trong config chỉ dùng cho `/healthz` probe của observability, không trigger work).

| Channel | Subject / Resource | Phía CMS publish/write | Phía worker consume |
|---|---|---|---|
| **Shared DB row** | table `cdc_system.cdc_worker_schedule` | API INSERT via `worker-schedule.create` (sync command) | Poller đọc table mỗi tick (xem `worker_server.go:626-639`) |
| **NATS cdc.cmd.\*** | 17 subject registered + 3 publish bypass | `CommandBus.Dispatch` hoặc `nc.Publish` trực tiếp | Worker subscribe từng subject |
| **NATS schema.config.reload** | `PublishReload(table, user, action, field)` | `NatsClient.PublishReload` | Worker subscribe stream `SCHEMA_CONFIG` |

→ **A** không gọi worker theo nghĩa RPC: CMS chỉ INSERT row vào DB, worker tự polling.
→ **B** đi qua NATS `cdc.cmd.*` (chủ yếu là CommandBus, một số bypass).
→ **C** không thuộc CMS: CMS không có Kafka consumer (verified via grep `kafka.NewConsumer|sarama|kgo|kafka.NewReader|ConsumePartitions` → 0 match). CMS chỉ gọi REST của Kafka Connect để **quản lý connector** (Debezium), không consume topic.
→ **D** worker tự subscribe `cdc.evt.*.completed` và update DB `cdc_jobs.finished_at` qua shared DB; CMS không subscribe để trigger gì cả (chỉ `SubscribeSync` ngắn hạn cho request/reply introspection).

## D — NATS-event chain

CMS **không subscribe** `cdc.evt.*.completed` để trigger work tiếp theo. Theo `job_repo_gorm.go:6-7,162-167`:

> The CommandBus writes rows here on Dispatch; the worker's JobMonitor closes them out via the wildcard `cdc.evt.*.completed` subscription (Phase 2 v2 / P3).
>
> UpdateStatus is the close-loop transition called by JobMonitor when a `cdc.evt.*.completed` arrives.

→ **JobMonitor nằm BÊN WORKER**. Worker subscribe wildcard, parse header `Cdc-Job-Id`, gọi thẳng SQL `UPDATE cdc_system.cdc_jobs … WHERE id=<job_id>` qua shared DB. CMS chỉ đọc lại row qua `GET /api/jobs/:id`.

`SubscribeSync` duy nhất phía CMS là **request/reply ngắn hạn** trong `internal/api/introspection_handler.go:39,92,139,162,196` — sub vào `cdc.evt.introspect.*.<correlationID>` để chờ kết quả introspection 1 lần rồi unsubscribe.

→ Loại D không có "CMS gọi worker" — đây là loop nội bộ worker, CMS chỉ là observer của trạng thái cuối qua `cdc_jobs` table.

3. **PublishReload payload** dùng `map[string]string` — `timestamp` là string RFC3339, không có version hay sender ID → khó debug khi nhiều caller publish cùng table.
