
### Schedule id=2 thì sao mà fire được lúc 16:35:09?
- id=2 (transform global, interval=5min) stored `09:29:22 local` (=
  `02:29 UTC actual`). Read back `09:29:22 UTC`.
- now tại 16:35:09 local = `09:35:09 UTC actual`. now.Sub
  = `09:35 - 09:29 = +6m > 5min` → FIRE.
- → id=2 catch up vì stored "future-UTC" đã lùi vào quá khứ.
- Sau khi fire, last_run_at = `time.Now()` instant = `09:35:09 UTC` →
  store wall-clock = `16:35:09 local`. Đọc lại = `16:35:09 UTC` →
  next fire tại UTC actual ≥ `16:35:09 UTC` = `23:35:09 local`. Pattern
  lặp lại — id=2 sẽ stuck 7h nữa.

### Code `HandleBatchTransform` — KHÔNG có chunking
File: `centralized-data-service/internal/handler/command_handler.go:966-1065`
```go
func (h *CommandHandler) HandleBatchTransform(msg *nats.Msg) {
    targetTable := string(msg.Data)
    ...
    rules, _ := h.mappingV2Repo.GetActiveRulesBySourceTable(ctx, sourceTable)
    var setClauses, whereClauses []string
    for _, rule := range rules {
        if !rule.IsActive { continue }
        castExpr := buildCastExpr(rule.SourceField, rule.DataType)
        quotedCol := quoteCommandIdent(rule.TargetColumn)
        setClauses  = append(setClauses,  fmt.Sprintf("%s = %s", quotedCol, castExpr))
        whereClauses = append(whereClauses, fmt.Sprintf("%s IS NULL", quotedCol))
    }
    setClauses = append(setClauses, "_updated_at = NOW()")

    transformSQL := fmt.Sprintf(`UPDATE %s SET %s WHERE _raw_data IS NOT NULL AND (%s)`,
        quoteCommandQualifiedTable(schemaName, targetTable),
        strings.Join(setClauses, ", "),
        strings.Join(whereClauses, " OR "),
    )

    execDB := h.db
    if h.shadowDB != nil { execDB = h.shadowDB }
    result := execDB.Exec(transformSQL)  // ← 1 statement, không chunking
    ...
    h.publishResult(msg, CommandResult{
        ...
        RowsAffected: int(result.RowsAffected),
        Status:       "success",
    })
}
```

- KHÔNG có loop, KHÔNG có `LIMIT`, KHÔNG có `OFFSET`, KHÔNG có batch size.
- WHERE `_raw_data IS NOT NULL AND (col_i IS NULL OR …)`:
  - `_raw_data IS NOT NULL` chỉ skip row chưa có raw.
  - `(col_i IS NULL OR …)` chỉ skip row đã typed đầy đủ — đây là cơ
    chế **idempotent**, không phải chunking.
- Nếu shadow table có 130 row: 1 UPDATE → rows_affected ≤ 130.
- Nếu shadow table có 1M row chưa transform: 1 UPDATE → rows_affected
  có thể tới 1M → long lock, large WAL, có thể trigger
  `statement_timeout`. **Rủi ro tải cao chưa được handle**.

Các `LIMIT 1000` trong cùng file ở line 1097 và 1180 thuộc về
`HandleScanRawData` + `HandlePeriodicScan` — chỉ giới hạn sample khi
scan JSONB keys, **không** áp dụng cho UPDATE transform.

### B. Thêm chunksize cho `HandleBatchTransform`
Nếu lo tải khi table lớn:
```sql
-- pseudo:
UPDATE shadow_x SET col_i = … WHERE id IN (
    SELECT id FROM shadow_x
    WHERE _raw_data IS NOT NULL AND (col_i IS NULL OR …)
    ORDER BY id LIMIT 1000
);
-- loop until rows_affected < 1000
```
Hoặc dùng `WHERE id > $cursor ORDER BY id LIMIT 1000` chunk theo PK.
Cần thêm:
- Config `transform.chunk_size` (default ví dụ 1000).
- Loop trong handler hoặc trong scheduler — chi tiết phải bàn.
- Activity log nên ghi cumulative `rows_affected` hoặc chia chunk.

Hiện tại table 130 row → chưa cần. Chuẩn bị trước khi data tăng.
